## 2. 产品定位与范围

CPDS 是可部署在笔记本电脑或 CCU 上的通信保障配置包下发工具。Windows版本以Wails桌面窗口呈现，CCU版本以普通浏览器页面呈现；Go后端负责文件解析、UDP广播、状态管理和日志记录。

CPDS 采用 Go + Vue 3 技术栈，Windows桌面版本增加Wails桌面外壳：

- Go 后端负责通信包解析、UDP 协议、文件传输、会话状态、日志以及前端接口。
- Vue 3 前端负责页面、用户操作和实时状态展示，不直接收发 UDP 报文。
- `CPDS.exe`使用Wails承载相同的Vue 3页面和Go业务后端，作为Windows原生桌面窗口运行，不启动外部浏览器。
- `CPDS-CCU`由Go服务提供Vue 3静态页面、HTTP API和WebSocket实时状态通道，用户通过普通浏览器访问。
- Windows与CCU版本共享页面组件、业务状态和后端核心代码，只允许宿主窗口能力与前后端通信适配层不同。
- CPDS项目目录独立保存三份需求文档和自己的 `proto/cpd.proto`，构建、测试和代码生成不得引用CPDC目录或工作区公共Proto文件。两项目的Proto保持相同 `package`、消息结构、字段号和枚举值，但使用各自的Go导入路径。

发布文件：

| 发布文件 | GOOS | GOARCH | 附加参数 |
|---|---|---|---|
| `CPDS.exe` | `windows` | `amd64` | Wails桌面外壳 |
| `CPDS-CCU` | `linux` | `amd64` | 无 |

本期左侧菜单仅显示并激活“参数加注”。“电台管理”“密钥管理”等入口隐藏且不提供业务功能。

本期功能范围：

1. 导入并解析通信保障配置包。
2. 显示组织、节点和节点设备配置。
3. 选择一个当前节点。
4. 发现当前二层广播域内的 CPDC。
5. 将上线 CPDC 与当前节点的逻辑设备自动配对并认证。
6. 广播传输原始通信保障配置包。
7. 展示各设备的发现、认证、接收、解析和完成状态。
8. 自动判定成功或失败并显示具体原因。

CPDS 启动下发后不支持暂停、取消或用户手动终止。

Windows Wails窗口在没有活动下发会话时允许正常关闭；下发会话进行中点击关闭按钮时必须拦截关闭并提示“下发进行中，暂不能关闭”，不能把窗口关闭作为终止流程的入口。最小化和最大化/还原始终可用。操作系统强制结束进程或设备断电按异常中断处理。

## 3. 部署与网络前提

- CPDS 支持部署在笔记本电脑或 CCU 上；部署在 CCU 上时，用户通过同一网络内的浏览器访问 CPDS 页面。
- CPDS部署在CCU上时，本机设备下发由独立运行的CPDC进程承担；CPDS本身不得自动计为CCU、Server或其他逻辑设备。
- CCU上的CPDS和CPDC必须安装在相互隔离的目录中，例如 `/opt/cpds/` 和 `/opt/cpdc/`。双方所有相对路径均以各自可执行文件所在目录为基准，不得以进程当前工作目录为基准。
- 笔记本、HF、CCU 外部网口以及经 CCU 网桥连接的 MultiBand 设备处于同一二层广播域。
- CCU 交换机侧网口与三个 MultiBand 网口已经加入同一网桥。
- 设备初始 IPv4 地址可以不在同一网段。
- CPDS 后端使用 IPv4 受限广播地址 `255.255.255.255` 与 CPDC 通信。
- CPDC固定接收UDP端口为 `39001`，CPDS固定接收UDP端口为 `39002`，`CPDS-CCU`网页固定使用TCP端口 `18080`。
- `CPDS.exe`由Wails内部WebView呈现页面，不要求占用对外网页端口；`CPDS-CCU`在CCU业务网络可访问的地址上监听 `18080`，浏览器通过 `http://<CCU业务IP>:18080/`访问。CCU版本的HTTP API和WebSocket复用同一TCP端口。
- CPDS只通过连接设备广播网络的业务有线网卡收发协议报文，业务网卡名称不属于CPD协议字段，也不得硬编码在业务代码中。`CPDS.exe`不接受网卡启动参数，由Windows Wails页面枚举和选择业务网卡；Windows必须排除无线、VPN、虚拟和环回网卡。只有一张候选业务网卡时自动选择；存在多张候选时优先恢复本机 `localStorage`键 `cpds.networkInterface`中仍然有效的选择，否则等待用户选择。没有有效选择时不得开始Distribution。
- `CPDS-CCU`不提供也不要求 `--interface`参数。每次Distribution开始时自动枚举所有合格的IPv4广播接口并冻结为本次会话接口快照，下次Distribution重新枚举。合格接口必须已启用、支持广播、不是环回或点对点接口、不属于无线/VPN/容器/常见虚拟接口，并具有非环回且非链路本地IPv4；Linux上属于网桥等上层接口的从属端口不作为独立三层出口，满足条件的逻辑网桥可以入选。
- Windows版为已选业务接口建立一个UDP广播发送套接字；CCU版为接口快照中的每个接口分别建立绑定其业务IPv4的广播发送套接字，并把同一数据报发送到每个套接字的 `255.255.255.255:39001`。Windows和Linux接收端统一以普通UDP套接字监听 `0.0.0.0:39002`，不读取也不依赖报文到达网卡索引，不按入站网卡过滤；报文内容不携带网卡名称。
- 接收端先校验Magic并反序列化Proto，再只接受当前有效 `session_id`且符合当前阶段消息类型的报文；设备回复还必须匹配发现或认证形成的设备类型、ESN和设备ID绑定。其他会话、未知设备、错误阶段、非法Magic或非法Proto报文直接丢弃，不更新状态。
- CCU版单个发送接口初始化或发送失败时记录接口名称、IPv4和错误并继续使用其他接口；没有任何发送接口成功初始化，或某次逻辑发送在全部业务接口上均失败时，才返回 `NETWORK_INTERFACE_ERROR`。接口运行中恢复后仍可继续尝试发送，单个接口错误不得立即终止Distribution。Windows和Linux的广播、环回和接收UDP套接字在初始化时产生的所有系统错误都必须包装为 `NETWORK_INTERFACE_ERROR`，不得降级为 `INVALID_MESSAGE`。
- CPDS每次逻辑发送无条件把完全相同的协议报文额外发送一次到 `127.0.0.1:39001`，确保本机CPDC不依赖操作系统的广播自回送行为。环回副本不随CCU业务接口数量重复；环回失败只记录告警，至少一个业务接口发送成功时不立即终止Distribution。CPDS不检测本机是否运行CPDC，也不增加同机部署开关。
- CCU多接口副本、环回副本和定时重发必须复用同一个 `session_id/message_id`和完全相同的消息体。Runner仍按单一逻辑数据流执行1 Mbit/s节流，每个广播接口约产生1 Mbit/s流量，CCU总出口约为 `成功接口数 × 1 Mbit/s`。
- CPDS接收端口与CPDC接收端口必须是两个不同的固定UDP端口，两个进程不得竞争绑定同一端口。
- Vue前端不得直接承担UDP通信；Windows Wails页面通过宿主绑定或事件获取状态，CCU浏览器页面通过HTTP API和WebSocket获取状态。
- 浏览器访问CCU上的CPDS使用HTTP/WebSocket单播，因此操作笔记本必须与CCU管理IP具备三层可达性；只有二层广播可达但IP单播不可达时，不视为满足CCU部署条件。
- 系统部署时应放行双方约定的 UDP 端口，并确认交换机 VLAN、端口隔离和 CCU 网桥规则不会阻断广播。
- CCU防火墙和服务运行环境必须允许所有合格业务接口上的UDP广播、环回接口上的UDP通信以及CPDS的HTTP/WebSocket端口；CPDS与CPDC应位于可以互通的网络命名空间。
- 本项目运行在物理隔离且可信的节点内部广播网，不要求对广播报文和通信包另行加密或进行密码学身份认证。CRC32和SHA-256仅用于传输完整性校验，不作为安全认证机制。
- 同一二层广播域在任一时刻只能有一个CPDS执行Distribution，并且只能接入当前待下发节点所属的设备。其他节点设备或第二个CPDS同时存在会导致额外设备、认证归属或会话竞争，本期不提供跨节点仲裁机制。

### 4.2 左侧文件导入区

左侧功能区保持 Figma 结构：

1. `File parse` 标题。
2. 已选择的原始文件名显示框；浏览器不得显示或依赖客户端完整文件路径。
3. `Browse` 按钮：打开浏览器所在终端的文件选择器，只允许选择 ZIP 文件，并将文件上传到CPDS后端临时目录。
4. `Parse` 按钮：上传成功后，校验并解析CPDS后端保存的临时副本。
5. `Net Node` 区域：显示包内解析出的组织和网络节点树。

解析前不得显示旧通信包的节点结果。解析失败时保留已选择的原始文件名，并显示可定位的失败原因。CPDS部署在CCU时同样采用浏览器上传，不允许把笔记本本地路径当作CCU文件路径使用。

### 4.4 右侧设备列表与通信包数据映射

选择节点后，CPDS读取该节点的 `SystemConfiguration`并按展示设备类型呈现设备引用；除 `CCU`与 `CCUAudio`共同归入一个“CCU”分组外，其余设备按逻辑设备类型分组。每个引用对应 `3_device_config/<设备ID>.json`。

| 包内配置位置或型号 | CPDS 逻辑设备类型 | CPDC 类型枚举 |
|---|---|---|
| `LANPrimary.Server`中的 `dc_server_*` | Server | `Server` |
| `LANPrimary.Server`中的 `dc_IEC_*` | IEC | `IEC` |
| `LANMember.CCU` | CCU-Main | `CCU` |
| `LANMember.CCU` | CCU-Audio | `CCUAudio` |
| `Radio.MMR200` | MMR200 | `MultiBandRadio` |
| `Radio.PMR200` | PMR200 | `MultibandHandheld` |
| `Radio.MR9360` | MR9360 | `HF` |
| `Radio.PRR206` | Small Handheld | `SmallHandheld` |
| `LANMember.VehInter` | VehInter | `VehInter` |

其中HF设备文件名匹配 `dc_MR9360_*.json`，SmallHandheld设备文件名匹配 `dc_PRR206_*.json`，VehInter设备文件名匹配 `dc_VehInter_*.json`。IEC和Server都使用 `SystemConfiguration.LANPrimary.Server`数组，但在同一节点内互斥：该数组只能引用 `dc_IEC_*`或 `dc_server_*`中的一种前缀，不能同时出现。CPDS分别将两种前缀映射为IEC和Server；前缀不匹配任何已知类型或同一节点同时包含两种类型时，通信包解析失败。

- `dc_ccu_10.64.0.1`：来自 `LANMember.CCU`，自动展开为共享该原始设备ID和配置文件的 `CCU-Main`与 `CCU-Audio`两个逻辑设备
- `dc_server_683771570`：来自 `LANPrimary.Server`

### 4.5 右侧状态区

右侧采用“按展示设备类型分组的紧凑状态卡片”方案，并保持 Figma 的尺寸、边框、背景和行高体系。`CCU-Main`与 `CCU-Audio`作为两行共同显示在同一个“CCU”分组内。

右侧顶部显示：

- 当前节点名称。
- 已上线逻辑设备数/期望逻辑设备数。
- Windows Wails版本在当前节点标题栏下方显示一行“业务网卡”控件，顺序固定为标签、网卡下拉框、“刷新”按钮和节点级“下发”按钮。该行采用已确认预览图的紧凑布局，新增控件不得改变标题栏、阶段条、进度条、设备卡片及其他既有控件的样式。
- CCU浏览器版本不显示业务网卡选择器和“刷新”按钮，节点级“下发”按钮保留在原标题栏位置；现有逐设备 `Inject` 按钮取消。
- 阶段条：发现、认证、传输、解析、完成。

Windows业务网卡控件遵循以下行为：

1. 页面启动时通过Wails宿主重新枚举当前已启用、支持IPv4广播且具有有效IPv4地址的候选有线网卡，Vue前端不直接访问系统网络接口。
2. 下拉项显示网卡名称和IPv4地址。只有一张候选时自动选中并显示“自动选中”；多张候选时，若 `cpds.networkInterface`保存的网卡名称仍在候选列表中则自动恢复，否则保持未选择状态并禁用“下发”。
3. 用户选择网卡后立即通知Go后端更新待用网卡，并将网卡名称写入 `localStorage`键 `cpds.networkInterface`。只保存网卡名称，不引入数据库或额外配置文件。
4. 点击“刷新”重新枚举候选列表：当前选择仍有效时保持不变；失效时重新执行“单候选自动选择—有效持久化值恢复—等待用户选择”的规则。枚举或选择失败时通过统一 `ErrorCode`和三语错误弹窗显示具体原因。
5. 点击“下发”时Go后端使用当前选择创建本次单网卡UDP传输；会话开始后冻结该网卡。活动Distribution期间下拉框和“刷新”按钮禁用，不能切换会话网卡。
6. Windows页面检测不到Wails宿主时按CCU浏览器模式呈现，不显示网卡选择行。业务网卡名称不写入通信包、Proto报文、节点数据或会话消息。

每个设备项显示：

- 包内设备类型及型号。
- 认证绑定的 ESN 后6位。前端不得显示完整39位ESN；完整值仅由后端用于协议匹配、排序和日志关联。
- 发现阶段报告的当前 IP。
- 当前阶段和状态。
- Transfer阶段显示接收进度条及百分比；其他阶段不显示进度条。
- 失败时显示由 `ErrorCode`映射得到的当前语言简短文案；完整信息可通过提示或详情查看，但不得由后端下发自由文本错误文案。

设备卡片不显示设备ID，并采用隐藏ID后的紧凑行高。设备ID仅保留在后端绑定、结构化失败信息和失败弹窗中。

解析阶段CPDC不持续上报解析状态或解析进度，因此CPDS不得显示“解析中”百分比或推测性进度。尚未收到最终解析结果的设备显示“等待解析结果”；收到最终成功或失败消息后再更新为“已完成”或“失败”。

CPDS后端向Vue提供的会话字段 `activeState`只允许以下稳定值，不写入UDP协议：

- `IDLE`
- `DISCOVERING`
- `AUTHENTICATING`
- `TRANSFERRING`
- `WAITING_PARSE`
- `DRAINING_AFTER_FAILURE`
- `COMPLETED`
- `FAILED`

前端会话结果中的 `failures`为数组，每项固定包含：

| 字段 | 说明 |
|---|---|
| `stage` | 失败所属发现、认证、传输或解析阶段 |
| `deviceType` | 失败设备类型，无法确定时为空 |
| `esnSuffix` | ESN后6位，未知时为空；不得返回完整ESN |
| `deviceId` | 已认证设备ID，未绑定时为空 |
| `errorCode` | 统一 `ErrorCode`枚举值 |
| `params` | 可选结构化参数对象，只允许路径、字段、期望值、实际值、上限、所需空间、可用空间、数量等原始数据，不得携带已拼接的自然语言句子 |

`activeState`和 `failures`属于CPDS的Go—Vue接口模型，不得加入Proto UDP消息。`errorCode`是前后端之间唯一的失败语义，Vue不得依据自由文本推导状态或错误类型。阶段、设备类型、ESN后6位、设备ID和错误参数等动态上下文使用上表的结构化字段传递，并由前端翻译模板通过参数插值生成完整句子。

CPDS前端使用与Vue 3兼容的维护版本 `vue-i18n`及Composition API实现国际化，支持简体中文 `zh-CN`、英文 `en-US`和阿拉伯文 `ar-SA`。默认语言为 `zh-CN`，任一翻译键缺失时回退到 `en-US`。所有用户可见文字，包括标题、按钮、菜单、表头、状态、校验提示、确认框、失败弹窗、计量单位和空状态，都必须提取为统一翻译键；包含文件名、数量、设备类型、ESN后6位等动态内容的句子必须使用命名参数插值，不得通过字符串拼接生成。

初始化配置至少满足 `legacy: false`、`locale: 'zh-CN'`和 `fallbackLocale: 'en-US'`；三套资源以完整语言标签注册，不使用只有 `zh/en/ar`的短标签替代。

语言切换菜单必须是可复用组件，切换后立即更新当前页面、设备状态和已经打开的失败弹窗，不重新执行Distribution。用户选择写入 `localStorage`键 `cpds.locale`，启动时优先读取有效保存值，无效值回退 `zh-CN`。每次初始化和切换都同步设置根元素 `<html lang>`与 `<html dir>`：中文、英文使用 `ltr`，阿拉伯文使用 `rtl`。

RTL适配必须覆盖布局而不仅是文字翻译：使用CSS逻辑属性实现内外边距、边框、定位和文本对齐；阿拉伯语下TopBar操作顺序、侧边栏位置、内容区左右分栏、展开箭头、前进/返回类图标和弹窗对齐按阅读方向镜像，传输进度值本身仍从0递增到100。不得在业务组件中散落针对阿拉伯语的硬编码像素覆盖。三份语言资源必须具有完全一致的键结构；自动化测试至少覆盖资源键一致性、默认与英文回退、即时切换、`localStorage`持久化、`html lang/dir`同步、RTL关键布局和带参数文案。

## 5. 通信包导入与解析

### 5.1 导入校验

CPDS必须校验整个通信包中的所有单位、节点和设备，不得只校验用户当前选择的节点。

#### 5.1.1 原始文件

1. 文件存在、可读取且大小大于0。
2. 原始文件名是以 `.zip`结尾的基本文件名，不得包含绝对路径、盘符、目录分隔符或 `..`。
3. 原始ZIP大小不超过1 MiB（1048576字节）。
4. 文件内容必须是合法ZIP，不得只按扩展名判断。
5. CPDS上传落盘后对保存的原始文件计算SHA-256；后续解析和下发必须使用这份已固定的文件，不能重新读取可能已被修改的浏览器本地源文件。

#### 5.1.2 ZIP安全校验

1. 拒绝加密ZIP。
2. ZIP条目只允许普通文件和目录，拒绝符号链接及其他特殊文件。
3. 每个条目路径规范化后必须仍位于业务根内；拒绝绝对路径、盘符、路径穿越、空路径和NUL字符。
4. 拒绝规范化后路径重复的条目；为保证Windows和Linux结果一致，也拒绝仅大小写不同但会形成同一路径的条目。
5. 读取每个普通文件直至结束并校验ZIP CRC；CRC失败时整个通信包无效。
6. 条目数量、压缩前后大小和累计值的计算必须执行整数溢出检查。
7. ZIP普通文件与目录条目总数不得超过4096，所有普通文件声明解压总量不得超过64 MiB，单个普通文件不得超过8 MiB，声明解压总量与ZIP原始大小之比不得超过200:1；任一限制超出时以 `INVALID_ZIP_SIZE`拒绝。
8. 规范化后的相对路径UTF-8长度不得超过1024字节，单个路径组件不得超过255字节。为保证Windows与Linux行为一致，路径组件还必须拒绝Windows保留设备名、冒号、末尾点号和末尾空格。

#### 5.1.3 业务根与目录

1. 必须存在 `0_contacts`、`3_device_config`、`4_net_node`和 `6_unit`。
2. 包含任何无线电设备时，必须存在 `1_resource`和 `2_radio_subnet`；一级资源目录统一且仅允许命名为 `1_resource`，不兼容其他名称。
3. `5_user`允许存在，但本期不参与节点树展示。
4. 原始通信包不包含 `local_node.json`。该文件是CPDC生成Server/IEC输出包时增加的产物，CPDS不识别、不解析、不校验其JSON内容，也不将其作为单位、节点、设备或引用关系的一部分。若输入ZIP意外携带该文件，只按普通ZIP条目执行通用路径、大小和CRC安全检查。
5. 原始业务目录应直接位于ZIP根。`txbz_json_v20.zip`多出的一层顶级包装目录属于CPDC输出参考样例的历史缺陷，不作为CPDS原始导入格式；CPDS不需要为了该输出样例兼容额外包装层。

#### 5.1.4 JSON与引用关系

1. 业务目录内所有JSON文件语法正确，根结构和实现本期功能所需的关键字段类型正确；不影响本期规则的未知字段允许忽略。
2. `File.Guid`允许是JSON数字或字符串，读取后统一转为字符串参与索引、比较和展示。
3. `0_contacts`中 `UnitTree/SubUnits/NetNodes`形成的单位和节点引用，必须分别解析到 `6_unit`和 `4_net_node`中的唯一文件。
4. 每个节点 `SystemConfiguration`引用的设备文件必须存在于 `3_device_config/<deviceId>.json`。
5. 同一节点内设备ID原则上不得重复；每个 `(deviceType, deviceId)`必须唯一。唯一例外是每个 `LANMember.CCU`引用必须自动展开为类型分别为 `CCU`和 `CCUAudio`的两个逻辑设备，二者共享同一个原始 `dc_ccu_*`设备ID和配置文件。CPDS的列表、状态、发现投影、认证及结果关联必须使用 `(deviceType, deviceId)`区分二者，不得只使用 `deviceId`作为关联键。
6. 任一节点解析出的逻辑设备数量不超过100；每个原始CCU引用展开后按两个逻辑设备计数。
7. 同一节点的 `SystemConfiguration.LANPrimary.Server`不得同时引用Server和IEC设备；二者为业务互斥类型。

#### 5.1.5 设备类型与无线电依赖

1. 设备引用位置、文件名前缀和逻辑类型必须符合第4.4节映射表；前缀不匹配任何已知类型，或出现在错误引用位置时，通信包无效。
2. 无线电设备的 `Channels`必须是JSON对象。每个频道中的 `Subnet`必须是非空文件名主体，不得携带路径字符，并且必须存在唯一的 `2_radio_subnet/<Subnet>.json`。
3. 多个频道允许引用同一个Subnet；该情况不视为错误，生成归档时按目标文件去重。
4. `MultiBandRadio`和 `MultibandHandheld`设备配置必须具有非空 `Alias`，用于生成 `PlanLocalUser`。
5. `HF`和 `SmallHandheld`首期按MMR200样例的公共字段结构校验，但不因缺少仅供 `PlanLocalUser`使用的Alias而拒绝通信包。
6. 节点ID、设备ID和原始文件基本名称的UTF-8长度不得超过255字节；Alias不得超过128字节且不得包含NUL、回车或换行，避免生成的INI结构被输入内容破坏。

只有通过文件、ZIP安全、目录结构、全部JSON、引用关系和业务字段校验的文件才能启用“下发”。校验失败时必须清空上一通信包的节点解析结果、禁用“下发”按钮，并使用 `errorCode + params`显示具体文件、字段、引用路径和失败原因；普通ZIP或校验失败的ZIP不得发送到CPDC，也不得进入任何CPDC正式输出目录。上传、计算SHA-256、ZIP读取和解析应采用流式处理，不得要求将整个1 MiB文件一次性载入内存。

### 5.2 ZIP目录与磁盘空间预检

CPDS在解压或解析前必须读取ZIP中央目录，累计所有普通文件声明的解压后大小，并估算本次处理所需空间：

`所需空间 = 原始ZIP + 解压内容 + 所有暂存输出 + 20%余量`

- 浏览器开始上传前，CPDS根据 `Content-Length`或等效文件大小信息检查原始ZIP临时落盘空间；上传完成并读取中央目录后，再按完整公式检查解压和暂存输出空间。任一检查不足都返回“导入失败：磁盘空间不足”，不得进入下发。
- `CPDS-CCU`与本机CPDC同设备运行时，为避免两个进程分别预检后共同占满磁盘，最低可用空间要求按上述所需空间的2倍计算。
- 解压过程中必须累计每个文件和全包的实际解压字节数，并与ZIP声明值对比。实际值超过声明值、计算溢出、CRC失败或超过已预留空间时立即终止并按无效通信包处理。
- 临时文件必须位于已通过空间检查的文件系统；检查不得只针对其他挂载点的总空间。
- 每次上传使用不可预测且与会话隔离的临时文件名，浏览器提供的原始文件名只能保存为元数据，不能直接作为临时路径。上传中断、大小超限、校验或解析失败时逐个删除本次明确命名的临时文件；新上传成功且当前无活动Distribution时逐个清理不再引用的旧上传副本。活动会话持有的不可变包副本在会话结束前不得清理或替换。
- CPDS启动时逐个清理能够确认属于未完成上传或已结束会话的遗留临时文件；无法确认归属的普通文件只记录告警，不执行递归或目录级删除。日志不得记录浏览器本地完整路径。

### 5.3 解析结果

解析成功后，CPDS应在内存中建立：

- 单位层级索引。
- 节点索引。
- 节点到期望设备类型、数量及设备 ID 的映射。
- 设备 ID 到设备配置文件的映射。
- 设备配置中可用于界面展示的 Alias、型号、目标 IP 等信息。

每个 `LANMember.CCU`引用在期望清单中形成一项 `CCU`和一项 `CCUAudio`。两项共享原始设备ID，在右侧同一个“CCU”分组内分别显示为 `CCU-Main`和 `CCU-Audio`，并分别展示各自CPDC实例的ESN、IP、状态和进度。

选择当前节点后，右侧期望设备列表立即刷新，之前节点的发现和下发状态不得混入当前节点。

## 6. 下发入口与状态管理

“下发”按钮仅在以下条件同时满足时启用：

- 通信包解析成功。
- 已选择一个当前节点。
- 当前没有正在执行的下发会话。

点击“下发”后，CPDS自动执行：发现 → 认证 → 文件传输 → 等待CPDC解析 → 完成确认。每个CPDC在本机文件接收完成后可以立即解析，不必等待其他CPDC传输完成；CPDS全局阶段仍保持“传输”，直至所有必需CPDC完成传输。CPDS必须在任意全局阶段及时处理并ACK已经到达的解析最终结果。

点击“下发”时，CPDS后端必须为本次会话创建不可变输入快照，至少固定原始包临时副本路径、原始文件名、SHA-256、文件大小、`expanded_size`、`required_workspace`、当前节点、期望设备清单和认证绑定。会话运行期间不得重新读取浏览器本地源文件，也不得因其他浏览器连接、重新上传、重新解析或切换节点改变该快照。活动会话期间后端必须拒绝Browse上传提交、Parse请求和节点切换请求；前端同时禁用对应控件。该约束由Go后端强制执行，不能只依赖单个页面的按钮状态；同一CPDS进程全局只允许一个活动Distribution。

发现或认证阶段失败时，CPDS立即结束本次Distribution并弹窗显示具体原因。传输或解析阶段出现失败时，CPDS把该设备标记为失败终态并将会话标记为“最终失败、正在完成其他在线设备”，不得中止其他非终态设备；全部期望CPDC均进入成功或失败终态后，才结束会话并弹出最终汇总失败信息。

设备一旦进入成功或失败终态，CPDS不得使用该设备随后到达的START响应、进度、缺包或传输完成消息改写其终态；重复的 `PARSE_COMPLETE_REQ`仍按幂等规则回复ACK。CPDS为其他非终态设备继续发送的广播不会要求终态CPDC再次参与，下一次Distribution从新的发现阶段和新的 `session_id`开始。

CPDS以16字节UUID v4 `session_id`隔离每次下发，会话结束后仍保留本次结果供用户查看。再次点击下发必须创建新 `session_id`。CPDS与CPDC的UDP消息使用“4字节Magic前缀 + [`proto/cpd.proto`](../../proto/cpd.proto)定义的Proto3二进制 `Packet`”封装，不使用JSON或gRPC。Magic固定为 `0xEEDDCCBB`，按网络字节序编码为 `EE DD CC BB`。

每条逻辑消息首次发送时生成一个16字节UUID v4 `message_id`；同一逻辑消息的广播副本、环回副本和定时重发复用相同ID及相同消息体，新逻辑消息使用新ID。RSP或ACK直接复制触发它的NTY或REQ的ID，不增加 `nty_message_id`、`req_message_id`或 `ack_message_id`。`message_id`只用于关联和幂等，不作为设备身份、安全凭据或额外业务判定条件。

CPDS发送的 `TRANSFER_START_NTY`必须携带原始文件名和32字节原始SHA-256。CPDC会维护最近一次接收并校验成功的 `./txbz/`原始包缓存：缓存文件名和实际哈希均匹配时可以跳过文件接收，并以 `TRANSFER_STAGE_CACHE_REUSE`返回成功 `TRANSFER_COMPLETE_RSP`；CPDS在设备状态和日志中显示“复用已接收原始包”。缓存命中只优化传输，本次认证、成功应用快照、节点ID、设备ID和文件包即使全部一致，CPDC也必须使用缓存包实际执行本次完整解析，不得直接回复解析成功。

CPDS收到某CPDC成功的 `TRANSFER_COMPLETE_RSP`后，一律为该实例启动独立35秒解析结果等待计时，为CPDC的30秒本地解析期限以及结果发送、调度留出余量。重复的传输完成回复不得重置计时。35秒内收到有效最终REQ时立即停止计时并回复 `PARSE_COMPLETE_ACK`：`result=RESULT_SUCCESS`时标记该实例成功终态；`result=RESULT_FAILED`时标记该实例失败终态，并记录统一错误码。35秒内没有收到有效最终结果时，以 `PARSE_TIMEOUT`标记该实例失败终态。迟到的有效 `PARSE_COMPLETE_REQ`仍需回复ACK以停止CPDC重发，但不得改写已经确定的超时失败终态。其他设备仍在传输、补发或解析不得暂停或重置该计时；单个实例解析失败或超时不得终止其他非终态设备。

成功 `PARSE_COMPLETE_REQ`表示CPDC已经写入全部正式输出并更新成功快照，ACK只表示CPDS已经收到该结果。CPDS发送ACK后无法判断ACK是否被CPDC收到，不得把“CPDC未确认收到ACK”列为服务端失败条件。成功和失败共用 `PARSE_COMPLETE_REQ/PARSE_COMPLETE_ACK`，不定义独立解析失败消息。

## 7. 发现与认证显示需求

### 7.1 发现成功判定

CPDS在5秒发现窗口内每隔1秒广播一次 `DISCOVER_NTY`，在第5秒结束前不提前进入认证。窗口结束后，按当前节点解析出的设备类型及数量，与窗口内所有 `DISCOVER_RSP`中的逻辑设备类型及数量统一比较：

- 类型和数量完全一致：发现成功。
- 缺少设备、多出设备、ESN冲突或类型不符：发现失败。

多类型CPDC共享一个ESN，但其 `DISCOVER_RSP.device_types`中每个类型分别计为一个逻辑设备。CPDS同时记录发现回复直接携带的 `instance_nonce/current_ip/subnet_mask`；这三个字段不要求出现在后续阶段消息中。

`CCU-Main`与 `CCU-Audio`不是同一多类型CPDC的两个身份，而是两个分别运行的CPDC实例。前者配置 `deviceTypes: ["CCU"]`，后者配置 `deviceTypes: ["CCUAudio"]`，二者必须使用各自独立的ESN。对于每个包内CCU引用，发现成功要求同时发现一台 `CCU`和一台 `CCUAudio`；任一类型缺少、多出或数量不一致均按发现失败处理。

每收到一条合法发现回复，CPDS必须立即把该实例按既定的“设备类型内ESN升序 × 通信包设备顺序”规则临时投影到右侧期望设备列表，实时显示已上线数量、ESN后6位、当前IP和“已发现”状态。临时投影只用于界面显示，不生成认证绑定，也不允许提前结束完整5秒发现窗口；发现最终失败时仍保留本轮已经发现的设备信息供用户排查。

同一发现窗口内，相同ESN且 `instance_nonce`不同表示不同运行实例发生ESN冲突，CPDS在第5秒统一结算时把本次发现标记为失败。弹窗显示冲突ESN后6位、各实例IP、设备类型和足以区分实例的nonce摘要，并提示运维人员停止其中一台CPDC、将其 `cpdc_config.json.esn`清空后重新启动。CPDS不得发送要求CPDC自动更换ESN的网络消息。

### 7.2 自动配对

同一设备类型存在多个实例时：

1. 在线CPDC实例按固定39位ESN字符串升序排列。
2. 通信包内设备保持 `SystemConfiguration` 数组原始顺序。
3. 两个列表按索引一一绑定。

认证后，CPDS后端维护最终ESN—设备ID绑定关系；右侧设备项只更新ESN后6位、IP和状态，不显示设备ID。

CPDS生成认证记录后、首次广播前必须执行唯一性校验：

- 每个 `(deviceType, ESN)`只能对应一个 `deviceId`。
- 每个 `(deviceType, deviceId)`只能对应一个ESN。
- 同一ESN可以对应不同 `deviceType`，用于多类型CPDC，但每种类型只能有一条绑定。
- 认证记录数量和类型计数必须与发现结果及当前节点期望清单一致。

校验失败时CPDS在本地以 `AUTH_ASSIGNMENT_CONFLICT`终止认证，不发送存在冲突的 `AUTH_NTY`。CPDC仍执行相同的防御性检查。CPDS收到 `result=RESULT_FAILED`的 `AUTH_RSP`时立即认证失败，不等待普通认证超时；`error_code=ERROR_CODE_AUTH_CONFLICT`时显示冲突绑定，`ERROR_CODE_BUSY`时显示由当前语言资源映射的“设备仍在处理上一会话”。协议不定义独立的认证冲突或忙碌消息。

认证记录编码后的单个UDP负载不得超过1400字节，其中Magic占4字节、Protobuf Packet最多1396字节。全部认证记录无法放入一条消息时，CPDS按 `4 + proto.Size(Packet)`和完整记录边界生成多条相互独立的 `AUTH_NTY`，每条消息包含一部分完整认证记录。认证从第0秒开始发送完整一轮；尚未结束时在第1、2、3、4秒分别重发完整一轮。认证记录不得跨消息截断，也不增加分片编号或重组字段。

5秒是认证最大窗口而非固定等待时间。全部预期CPDC返回成功 `AUTH_RSP`时立即进入Transfer，不再发送剩余认证轮次；任一失败 `AUTH_RSP`立即导致认证失败；到第5秒仍缺少成功回复时以认证超时失败。发现阶段仍必须完整等待5秒，不允许提前成功。

CPDS使用本项目自己的 `CPDS/internal/protocol/timing.go`集中定义发现、认证、传输及等待解析结果等时间参数，不依赖或导入CPDC源码。CPDS后端和Vue前端均不得在其他位置硬编码时间数值；Vue所需的倒计时或状态时间由Go后端提供。

## 8. 文件传输显示需求

- CPDS默认按1 Mbit/s名义文件负载速率对UDP数据分包进行节流，不得无节流地瞬间发送整个通信包；实际有效速率可以因系统调度、丢包和补发而降低。该值在CPDS工程自己的 `CPDS/internal/protocol/transfer.go`中以 `TransferPayloadRateBitsPerSecond = 1_000_000`集中定义，不属于CPDC配置或双方协议协商字段。
- 进度条只在Transfer阶段显示；发现、认证、解析和完成阶段均不显示任何发送或设备进度条。
- Transfer阶段在阶段条下方显示独立的“CPDS发送进度条”，并同时显示已发送分包数/分包总数和百分比。
- 首轮发送进度按“首轮已发送分包数/分包总数”连续计算；它不代表任何一台CPDC的接收进度。
- 首轮发送完成后，发送进度保持100%。进入缺包补发时，进度条旁改为显示“补发中”和当前待补发分包数量，不重新从0%开始。
- 每台CPDC的接收进度以CPDC报告的约30%、60%、100%为准。
- CPDC报告缺包时，对应设备显示“补发中”及已知接收进度。
- 首轮数据发送期间不执行10秒设备静默计时。第一次发送 `TRANSFER_END_NTY`后，每个CPDC使用单调时钟分别启动自己的10秒回复计时器。
- 只有某设备自身的有效回复可以重置该设备的10秒计时器。CPDS发送START、END、收到其他设备回复或为其他设备补包，均不得重置或暂停该设备计时器。
- CPDS正在补发某设备自身请求的缺失分包时，只暂停该设备的10秒计时器；该轮补发结束并发送END后恢复计时。其他设备的计时器继续运行。
- 首轮数据发送前连续广播2次 `TRANSFER_START_NTY`；数据发送持续超过1秒时，发送期间每1秒补发一次开始通知。
- 首轮发送结束后再次广播2次 `TRANSFER_START_NTY`，再广播 `TRANSFER_END_NTY`并进入设备结果等待状态。
- 等待结果期间需要重试时，每1秒按顺序发送一次 `TRANSFER_START_NTY + TRANSFER_END_NTY`，不能只发送结束通知。
- 每轮缺包补发完成后发送一次 `TRANSFER_START_NTY + TRANSFER_END_NTY`。
- 任一必需CPDC返回 `result=RESULT_FAILED`的 `TRANSFER_COMPLETE_RSP`时，CPDS将该设备标记为失败终态并停止仅针对该设备的补发，同时记录其阶段、错误码和原因；PRECHECK阶段常见原因包括包大小或开始参数非法、认证绑定缺失和磁盘空间不足，RECEIVE/VERIFY阶段还包括文件读写、大小及哈希失败。CPDS继续完成其他非终态设备。
- 第一次END后，某设备连续10秒没有自身有效回复时，将该设备标记为传输失败终态；不能用其他设备的消息替它续期。
- CPDS根据某设备最新进度回复和缺包区间计算其唯一有效接收分包数并维护接收高水位。某设备虽持续有效回复，但高水位连续30秒没有增加时，将该设备以“传输无进展”标记为失败终态；只要高水位继续增加，缺包补发不限制轮数。
- 只要仍收到缺包回复，CPDS持续补发，不限制补发轮数。
- `TRANSFER_END_NTY`消息体为空；文件名、大小、SHA-256和分包总数只取自当前会话START。单个CPDC使用多条 `TRANSFER_LOSSPACK_REQ`上报缺包区间时，每条都是可独立处理的完整请求。CPDS不回复ACK，收到有效REQ后立即把区间并入待补发集合，不等待分片重组；重复区间必须幂等合并，丢失REQ由下一次END触发的重新检查覆盖。

CPDC解析成功还必须满足以下正式输出约束，任一步失败均通过 `PARSE_COMPLETE_REQ`报告解析失败，CPDS不得把该设备标记为成功：

- `CCU`在 `./txbz_ccu/`生成对应 `dc_ccu_*.json`后，只删除相对CPDC可执行文件目录的 `../../update/`直属目录下匹配 `dc_ccu_*.json`的普通文件，不递归且不处理子目录或其他文件；随后将配置复制到该目录并递归清空、保留 `./txbz_ccu/`根目录，成功时配置只保留在 `../../update/`。`CCUAudio`的目标目录是 `../update/`，写入前执行相同的匹配文件清理规则。
- `Server`和 `IEC`在保留现有 `./txbz_server/<原始通信包文件名>`输出的同时，都递归清空并保留相对CPDC可执行文件目录的 `../txbz_data/`根目录，再按原始通信包文件名去掉末尾 `.zip`扩展名创建子目录，将包含本次 `local_node.json`的各自完整输出包解压到 `../txbz_data/<原始通信包文件名去掉.zip>/`。
- `./txbz_ccu/`和 `../txbz_data/`的递归清理删除目标根目录内全部文件和子目录，但不删除根目录本身；清理、复制或解压不建立回滚机制，失败时不得更新成功应用快照。

## 9. 弹窗与失败原因

每次Distribution失败都必须在前端显示弹窗。发现或认证阶段失败时立即弹窗；传输或解析阶段先在页面显示“已检测到设备失败，正在完成其他在线设备”，待全部期望CPDC进入成功或失败终态后再弹出最终汇总。弹窗至少显示：失败阶段、失败设备类型、ESN后6位（已知时）、设备ID（已绑定时）、统一错误码和具体原因；最终汇总还应分别列出成功完成、失败和掉线的全部设备。

典型原因包括：

- 通信包格式无效或引用文件缺失。
- 通信包超过1 MiB、ZIP声明大小异常或磁盘空间不足。
- 发现阶段缺少某类型设备或数量不匹配。
- 发现到当前节点不需要的额外设备类型。
- 不同CPDC实例使用相同ESN。
- 认证回复缺失。
- 认证记录唯一性校验失败，或 `AUTH_RSP`返回 `AUTH_CONFLICT/BUSY`失败码。
- 文件传输阶段设备失联。
- 文件传输阶段设备持续回复但连续30秒接收高水位没有增加。
- 文件大小、分包或整体哈希校验失败。
- CPDC通过 `result=FAILED`的 `PARSE_COMPLETE_REQ`上报解析失败。
- 某CPDC在收到其 `TRANSFER_COMPLETE_RSP`后的35秒内未上报有效 `PARSE_COMPLETE_REQ`。

## 10. 日志

CPDS应记录：

- 包导入和解析结果。
- 当前节点及期望设备清单。
- 每个阶段的开始、成功、失败时间。
- CPDC发现信息和最终绑定结果。
- 分包发送、缺包区间和补发轮次。
- 每台设备的进度与解析结果。
- 所有失败原因。

CPDS日志和前端可显示的结构化上下文统一执行以下脱敏规则：

- 不记录 `1_resource`中的密钥正文，也不记录设备配置中的密码正文，包括 `AdvancedPassword`和 `PrimaryPassword`。
- 对字段名包含 `password`、`passwd`、`secret`、`privateKey`或明确表示密钥内容的字段，按大小写不敏感规则把字段值替换为 `***`；脱敏必须在结构化数据序列化为日志或错误文本之前完成。
- 不记录原始UDP分包负载、完整ZIP内容或完整JSON正文。
- JSON解析失败时只记录文件路径、字段路径、错误类型和位置，不输出可能包含敏感内容的原文片段。
- 前端弹窗及发往CPDC的结构化协议字段不得包含密钥或密码正文；Proto失败消息只携带 `ErrorCode`，不携带自然语言原因。
- 文件名、设备ID、节点ID、SHA-256和分包序号允许正常记录。

## 11. 验收标准

1. CPDS能正确解析按本规范使用 `1_resource`且业务目录直接位于ZIP根的原始通信包；`txbz_json_v20.zip`只作为Server/IEC的CPDC输出产物参考，不属于CPDS原始导入包验收范围。
2. 左侧导航仅显示“参数加注”，左侧树能按样例包显示单位和网络节点；选择 A车后右侧显示一台MMR200、一台Server，以及一个包含 `CCU-Main`和 `CCU-Audio`两行的“CCU”分组，共四个逻辑设备。
3. 右侧设备卡片不显示设备ID，能清晰显示设备名称、ESN后6位、IP和状态；仅Transfer阶段显示CPDS发送进度和设备接收进度。
4. 每秒发送一次 `DISCOVER_NTY`，完整等待5秒后统一判断全部 `DISCOVER_RSP`；数量不匹配时立即给出明确失败信息。
5. 认证、传输、解析状态与交互流程文档一致。
6. 首轮发送无10秒静默超时；第一次END后每个CPDC独立累计10秒自身回复计时，只在补发该设备自身请求的分包期间暂停。其他设备的回复、补发或CPDS发送START/END不得替它续期。
7. 缺包持续存在时能够持续补发，不受固定轮数限制。
8. 下发过程中界面不提供暂停、取消或终止操作。
9. CPDS与CPDC部署在同一台CCU时，本机CPDC能够完成发现、认证、接收和解析，且不依赖Linux广播自回送。
10. CPDS部署在CCU时，网络可达的笔记本能够通过CCU管理IP访问页面并持续接收实时状态。
11. CPDC在全局传输阶段提前通过 `PARSE_COMPLETE_REQ`上报成功或失败时，CPDS能够立即返回 `PARSE_COMPLETE_ACK`并正确更新对应设备状态。
12. Windows Wails或CCU浏览器上传1 MiB以内的ZIP时，CPDS以流式方式保存、校验和解析，不依赖客户端本地路径。
13. 认证记录超过单个1400字节UDP负载时能够生成多条独立 `AUTH_NTY`，CPDC从这些消息中正确累计自己的多类型绑定。
14. 缺包区间超过单个1400字节UDP负载时能够按 `4 + proto.Size(Packet)`生成多条独立 `TRANSFER_LOSSPACK_REQ`；CPDS不回复ACK，逐条幂等合并并只补发所有CPDC实际缺失分包的并集。
15. `LANPrimary.Server`只引用 `dc_server_*`或只引用 `dc_IEC_*`时分别识别为Server或IEC；同一节点同时引用两种前缀时导入失败并显示互斥冲突。
16. 普通ZIP、缺少业务目录的ZIP、设备引用缺失或关键业务字段无效时，导入失败且“下发”按钮不可用；该文件不会发送到CPDC或进入任何CPDC正式输出目录。
17. 原始ZIP超过1 MiB时导入失败；ZIP中央目录声明异常、空间计算溢出或磁盘空间不足时显示明确的“导入失败”原因。
18. CPDS在解压前完成空间预检，解压期间累计实际写入量；实际写入超过目录声明或预留量时停止处理，不产生可下发结果。
19. CPDS与本机CPDC同设备运行时，CPDS按单次所需空间的2倍检查可用空间。
20. CPDS发送前检测到认证映射不唯一时，不发送认证消息并以 `AUTH_ASSIGNMENT_CONFLICT`失败；收到 `ERROR_CODE_AUTH_CONFLICT`或 `ERROR_CODE_BUSY`的失败 `AUTH_RSP`时立即失败，不等待认证窗口超时。
21. 对小于1秒即可完成首轮发送的包，即使CPDC丢失首部两次 `TRANSFER_START_NTY`，仍能依靠尾部开始通知、结束通知和全量缺包补发完成传输。
22. Windows版使用Wails窗口运行，最小化和最大化按钮有效；下发会话执行期间关闭按钮不得终止进程。CCU版通过普通浏览器访问，不承诺浏览器窗口控制能力。
23. 某CPDC返回成功 `TRANSFER_COMPLETE_RSP`后35秒内未上报有效 `PARSE_COMPLETE_REQ`时，CPDS以 `PARSE_TIMEOUT`把该设备记为失败终态并继续完成其他非终态设备；迟到结果只ACK、不改写终态，最终会话不会永久停留在等待解析结果状态。
24. `PARSE_COMPLETE_REQ`使用 `result=SUCCESS/FAILED`统一表达解析成功和失败，CPDS对两种结果均返回 `PARSE_COMPLETE_ACK`。
25. CPDS发送成功结果ACK后即按已送出确认处理；无法获知CPDC是否实际收到ACK，不把ACK送达状态作为CPDS侧失败条件。
26. `TRANSFER_START_NTY`携带32字节原始文件SHA-256，`TRANSFER_END_NTY`消息体为空；CPDS不发送或等待 `TRANSFER_LOSSPACK_ACK`。
27. 某CPDC缓存文件名和实际SHA-256匹配时，CPDS接受其缓存复用传输结果并等待本次重新解析；即使缓存、认证和成功应用快照全部匹配，也不接受未实际解析就直接上报的成功结果。
28. CPDS发送时在序列化Packet前拼接大端Magic `EE DD CC BB`；接收时先校验Magic，不匹配则直接丢弃，匹配后才反序列化Packet。Packet不超过1396字节，完整UDP负载不超过1400字节，Packet内部不包含 `magic/version/timestamp/nty_message_id/req_message_id`。
29. 发现或认证阶段失败时立即结束并弹窗；传输或解析阶段某设备失败时继续完成其他非终态设备，待全部设备进入终态后弹窗汇总成功、失败和掉线明细。
30. 第一次END后，持续回复但连续30秒唯一有效接收分包数没有增加的设备以“传输无进展”失败；其他在线设备继续完成传输和解析。
31. 加密ZIP、符号链接、路径穿越、规范化后重复路径、仅大小写不同的冲突路径或CRC错误均导致导入失败，且不产生可下发结果。
32. CPDS校验通信包中的全部节点；未选择节点中的引用缺失或业务字段错误同样导致导入失败。
33. `File.Guid`分别使用JSON数字和字符串时均可解析，并规范化为相同字符串语义。
34. 多个无线电频道引用同一个有效Subnet时导入成功，生成归档只包含一份对应文件；`Radio.MR9360`和 `Radio.PRR206`分别按HF和SmallHandheld识别。
35. 构造包含 `AdvancedPassword`、`PrimaryPassword`及大小写不同敏感字段名的设备配置和解析错误时，CPDS日志和弹窗中的结构化上下文均只显示脱敏值，不出现原始正文；协议只传错误码。
36. 认证未完成时在第0至4秒每秒发送一轮全部 `AUTH_NTY`；全部成功回复到齐时立即进入Transfer，失败回复立即失败，第5秒仍不完整时认证超时。
37. 修改 `CPDS/internal/protocol/timing.go`后，CPDS所有相关计时行为同步变化；后端和Vue中不存在第二份硬编码协议时间，也不依赖CPDC工程文件。
38. 两个不同nonce实例报告相同ESN时发现失败，弹窗提供可区分实例的信息及人工清空其中一台ESN的恢复说明；CPDS不会要求设备自动改号。
39. CPDS导入校验拒绝同一节点同时存在Server和IEC的通信包。
40. 默认1 Mbit/s时，1 MiB通信包首轮发送约8.39秒且不会触发传输静默超时；修改CPDS的 `TransferPayloadRateBitsPerSecond`后无需修改CPDC。
41. CPDS向Vue返回的 `activeState`只使用规定枚举；失败详情固定包含 `stage/deviceType/esnSuffix/deviceId/errorCode`及可选结构化 `params`，不返回完整ESN或自由文本错误原因。
42. 每个非零 `ErrorCode`在三套语言资源中都有文案；Distribution失败后切换语言可以立即重绘当前失败弹窗，协议和后端无需重新提供错误字符串。
43. 同一逻辑消息的广播、环回和重发复用一个 `message_id`，RSP/ACK复制触发消息的ID；系统不定义额外ID字段，也不把ID用于业务身份或安全判断。
44. Windows和CCU版本均无条件发送环回副本；未部署本机CPDC时不影响远端流程，部署本机CPDC且广播自回送被阻断时仍可完成Distribution。
45. `zh-CN`、`en-US`和 `ar-SA`语言资源键结构完全一致；默认中文、缺失键回退英文，切换语言后页面和已打开弹窗立即更新，刷新后从 `cpds.locale`恢复选择。
